# Namespace Lab: Architecture & Metrics Specification

This document provides a detailed technical specification of the Minimalist Namespace Lab setup, the system variables tracked during execution, and the expected CSV data schemas for benchmarking.

---

## 1. Setup Configuration & Architecture

The lab models two distinct network topologies to compare data plane latency under synthetic network load:

### Topology A: Traditional Sidecar (Proxy-Based)
```
[Root Host NetNS]
  |
  +-- (Fortio client) -- [10.0.0.10:80] 
                           |
                           +-- [iptables NAT Redirect]
                                 | (Port 80 -> 8080)
                                 v
                               [socat proxy] (ns_victim, CPU 1)
                                 | (Loopback forward)
                                 v
                               [HTTP Server] (ns_victim, CPU 1)

[Attacker NetNS] (CPU 2)
  |-- (wrk2 load generator) --> [10.0.0.1:8000] (Host Dummy Server)
```
* **Traffic Flow:**
  - Client traffic entering the Victim namespace is captured by `iptables` NAT redirection rules and sent to the local user-space proxy (`socat`).
  - `socat` opens a new TCP connection to the local HTTP server.
  - This path incurs two user-to-kernel context transitions, socket buffer queueing, and TCP stack overhead.
* **Attacker Load:**
  - Runs in a separate namespace `ns_attacker`.
  - Sends high-volume traffic to a host-bound dummy endpoint `10.0.0.1:8000`, using network resources but avoiding user-space proxying in the victim path.

### Topology B: Sidecarless eBPF (Kernel-Based)
```
[Root Host NetNS]
  |
  +-- (Fortio client) -- [10.0.0.10:80]
                           |
                           | (Direct network routing)
                           v
                       [TC eBPF clsact Filter] <---> [Shared BPF Hash Map]
                           |                           (Spinlock contention)
                           v
                       [HTTP Server] (ns_victim, CPU 1)

[Attacker NetNS] (CPU 2)
  |-- (wrk2 load generator) --> [10.0.0.1:8000] (Host Dummy Server)
                                    ^
                                    | (Intercepted by TC eBPF clsact)
```
* **Traffic Flow:**
  - Client traffic flows directly to the container HTTP server.
  - The eBPF program is attached to the host-side veth interfaces (`veth-vic-br` and `veth-att-br`) via TC.
  - For every packet (from both victim client and attacker), the eBPF code intercepts the frame, parses the flow keys, and queries/updates a shared, global pinned hash map `flow_map`.
  - Under load, this creates bucket-level spinlock contention inside the kernel hash table.

## 2. Measuring Variables

To evaluate performance, the test scripts capture variables across both user-space and kernel-space:

### Client-Side Performance (Via `fortio`)
* **`P50_Latency_ms`**: Median latency of requests.
* **`P90_Latency_ms`**: 90th percentile latency. Shows early tail-latency trends.
* **`P99_Latency_ms`**: 99th percentile latency. Focus of SLA/microservice SLO measurements.
* **`P99.9_Latency_ms`**: 99.9th percentile latency. Reveals extreme tail outliers.
* **`Throughput_RPS`**: Achieved transaction rate of the victim path.

### Kernel Overhead (Via `bpftrace`)
* **`Context_Switches`**: Count of scheduler context switches (`sched:sched_switch`). Crucial for measuring the impact of user-space proxy scheduling.
* **`Net_RX_SoftIRQ_Latency_ns`**: Time spent processing net packet receive interrupts in softirq context.
* **`Map_Lookup_Latency_ns`**: The execution latency of the hash map lookups (`htab_map_lookup_elem`).
* **`Map_Update_Latency_ns`**: The execution latency of hash map updates (`htab_map_update_elem`).
* **`Spinlock_Contention_Count`**: Call count of `queued_spin_lock_slowpath`. High counts indicate that cores are stalling waiting for eBPF map bucket locks.

## 3. Expected CSV Format

To parse the raw JSON outputs (from `fortio`) and text files (from `bpftrace`), compile the results into a consolidated CSV using the following schema.

### CSV Columns (Schema)
| Column Name | Type | Description |
| :--- | :--- | :--- |
| `Architecture` | String | `sidecar` or `sidecarless` |
| `Attacker_RPS` | Integer | Background load generated by attacker (`0`, `10000`, `20000`, `30000`) |
| `P50_Latency_ms` | Float | 50% percentile transaction latency |
| `P90_Latency_ms` | Float | 90% percentile transaction latency |
| `P99_Latency_ms` | Float | 99% percentile transaction latency |
| `P999_Latency_ms` | Float | 99.9% percentile transaction latency |
| `Context_Switches` | Integer | Total number of scheduler switches during the 30s run |
| `Map_Lookup_Avg_ns` | Float | Average duration of `htab_map_lookup_elem` lookup (N/A for sidecar) |
| `Spinlock_Contention`| Integer | Total `queued_spin_lock_slowpath` calls captured during the run |

## 4. Key Performance Indicators (KPIs) to Observe

When analyzing the generated CSV data:
1. **Context Switches vs. Latency:** In `sidecar`, context switches scale linearly with traffic. Watch how `P99_Latency` correlates with increased context switching.
2. **Lock Contention vs. eBPF Latency:** In `sidecarless`, watch the tipping point where `Spinlock_Contention` spikes (around 20k-30k RPS). Notice how `Map_Lookup_Avg_ns` increases, directly degrading client tail latency despite bypassing the proxy.
